```text
Detect
   ↓
Investigate
   ↓
Correlate
   ↓
Contain
   ↓
Eradicate
   ↓
Recover
   ↓

```

# Detection

Security detection relies on telemetry generated by systems, applications, users, networks, and security tools.

Useful data sources may include:

```text
Authentication logs
Endpoint logs
Network logs
Firewall logs
DNS logs
SIEM events
IDS alerts
Cloud sign-in logs
```

The purpose of detection is to identify activity that may require investigation.

An alert itself is not automatically proof of compromise.

---

# Security Monitoring

Security monitoring helps analysts identify unusual or suspicious behaviour across an environment.

Examples include:

- repeated failed authentication
- unusual successful logins
- suspicious process creation
- unexpected network connections
- persistence mechanisms
- malicious file activity
- suspicious PowerShell commands
- unusual cloud authentication

The important part is correlating several pieces of evidence instead of relying on one event.

---

# SIEM

A Security Information and Event Management platform can collect and search security telemetry from many systems.

During investigation, SIEM queries can help answer questions such as:

```text
Which host generated the event?
Which user was involved?
What happened before the alert?
What happened afterward?
Was the activity repeated?
Is another system showing the same indicator?
```

This makes SIEM useful for both alert triage and deeper incident investigation.

---

## Alert Triage

One of the important concepts from this module was determining whether an alert has enough evidence to justify escalation.

A simple triage workflow is:

```text
Review alert
     ↓
Identify affected asset
     ↓
Review supporting logs
     ↓
Check user / process / network context
     ↓
Decide whether more investigation is required
```

I learned not to automatically describe unusual activity as malicious if the evidence does not support that conclusion.

---

# Incident Response

The incident response lifecycle helps organise what defenders do after suspicious activity is detected.

My simplified workflow is:

```text
Detection
   ↓
Analysis
   ↓
Containment
   ↓
Eradication
   ↓
Recovery
   ↓
Post-Incident Review
```

---

## Detection and Analysis

During this phase, the goal is to understand:

- what happened
- which system was affected
- which user was involved
- how the activity started
- what indicators are available
- whether persistence or lateral movement occurred

Evidence should be collected before destructive remediation when possible.

---

## Containment

Containment aims to limit the incident.

Examples include:

```text
Stop malicious process
Isolate affected host
Disable compromised account
Block malicious IP
Block malicious domain
Restrict network access
```

The appropriate containment action depends on the incident.

---

## Eradication

Eradication removes the cause or remaining malicious artefacts.

Examples include:

- deleting malware
- removing persistence
- removing malicious accounts
- patching exploited vulnerabilities
- resetting credentials
- removing malicious scheduled tasks

---

## Recovery

Recovery returns the system to a trusted operational state.

Important tasks may include:

- validating remediation
- restoring services
- monitoring for recurrence
- verifying user access
- confirming malicious artefacts are gone

# Evidence and Documentation

Good incident documentation should separate:

```text
Observed evidence
```

from:

```text
Analyst assumptions
```

For example:

```text
Observed:
Process attempted an outbound connection.

Not automatically proven:
The connection was successful C2 traffic.
```

This distinction improves the accuracy of incident reports.

---

# Indicators of Compromise

Useful incident indicators may include:

- IP addresses
- domains
- URLs
- file hashes
- usernames
- process names
- file paths
- registry keys
- scheduled tasks
- email addresses

Indicators become more useful when they are correlated with behaviour and context.

# Investigation Mindset

One of the most useful habits I developed was asking:

```text
What do I know?
What can I prove?
What still needs verification?
```

This helps avoid overconfidence during investigations.

For example:

```text
Alert generated
≠
Confirmed incident
```

and:

```text
Unusual connection
≠
Confirmed command-and-control
```

Additional context is often required.

# Key Takeaways

## 1. Alerts are investigation starting points

An alert should lead to questions and evidence collection.

It should not automatically determine the final verdict.

---

## 2. Correlation makes detection stronger

A single event may have little meaning.

Combining:

```text
User
+
Host
+
Process
+
Network
+
Time
```

can reveal a much clearer picture.

---

## 3. Evidence should be collected before remediation

Removing a suspicious file too early can destroy useful evidence.

Where possible, I should first document:

- file path
- process
- network activity
- persistence
- relevant logs
- indicators

---

## 4. Recovery requires verification

Removing malware is not enough.

The analyst should verify that:

```text
Process is gone
Persistence is removed
Malicious files are removed
Access is restored safely
No obvious recurrence remains
```

---

## 5. Documentation is part of incident response

A technically correct investigation still loses value if the findings are not documented clearly.

Good reports help:

- other analysts
- management
- incident responders
- future investigations

understand what happened and what actions were taken.
